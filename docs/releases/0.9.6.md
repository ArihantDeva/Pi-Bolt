Pi-Bolt 0.9.6 makes the everyday paths of a coding agent fast: reading a screenshot takes half a second of CPU instead of 37,
`@file` completion answers each key in under a millisecond, read-only tools start while the model is still writing, the
connection is warmed while you type, and long sessions cost up to 31% less CPU per prompt. The engine is new too. Pi is 1.3.0, as in [0.9.5](0.9.5.md).

Measured on GitHub's runners, 0.9.5 as released against 0.9.6, with the same local fake model (Linux pinned to one CPU; CPU time):

| | Linux x86-64 | Linux ARM64 | macOS | Windows |
|---|---|---|---|---|
| A prompt 40 into a long session (9 MB requests) | 93.7 → 64.8 ms | 78.2 → 53.8 ms | 66.0 → 50.8 ms | |
| A prompt 20 into a long session | 39.7 → 34.5 ms | 34.0 → 30.7 ms | 40.9 → 37.6 ms | |
| Streaming a 20,000-character answer | 0.81 → 0.68 s | 0.71 → 0.65 s | | 1.05 → 0.90 s |
| Streaming a 60,000-character answer | 2.27 → 2.25 s | 2.25 → 2.05 s | | 3.57 → 3.07 s |
| An interactive session (5 prompts) | 143 → 133 ms | 183 → 175 ms | 202 → 193 ms | 285 → 281 ms |
| A headless prompt (5 model turns) | 78 → 76 ms | 57 → 56 ms | 71 → 69 ms | 107 → 103 ms |

Startup and idle are unchanged; memory in an interactive session is 3–13% lower (macOS footprint 41 → 37 MB, Windows working set
49 → 42 MB). The rows for streaming and the interactive session on Linux are averages of 4 and 31 runs.

### Images

- **Reading a screenshot** with the `read` tool takes about 0.5 s of CPU instead of 37 s (2442x1438 PNG), and a 4032x3024
  photo about 1.1 s instead of 76 s: images over the limits are resized with the runtime's native image code (`Bun.Image`)
  instead of WebAssembly, which the default builds run without a JIT. The sizes, formats and note sent to the model follow the
  same rules; the bytes differ slightly (photon is used where the native code is not available).
- **Images within the limits** are not decoded again: a PNG or WebP that fits is checked natively and sent as it is (1800x1100
  PNG: 47 ms instead of 1.0 s; WebP: 68 ms instead of 6.3 s), and a JPEG is decoded once instead of twice. A damaged image is
  still reported as omitted, as before.

### A turn

- **Read-only tools start while the model's message is still arriving.** `read`, `ls`, and `grep` and `find` (searched
  in-process) start as soon as their call is complete, so after a message with tool calls the next request goes out about 3 ms
  after the message ends instead of 80–200 ms. Only while no extension other than the built-in MCP one hooks tool calls; events,
  the session file and what extensions see are the same.
- **The connection is warmed while you type.** After 10 s without model traffic, starting to type opens the connection to the
  endpoint the last request used (OpenAI-compatible and Anthropic APIs), so the handshake (often 50–300 ms) is done before Enter. Nothing is sent but the TLS
  handshake.
- **Long sessions:** each request is built from the previous request's bytes plus what is new, not serialized whole again:
  21% less CPU per prompt at 40 prompts, 13% at 20 (byte-identical bodies over 1,017 compared requests).
- **Events:** JSON, RPC and ACP mode write their output in batches, events without an extension handler are delivered without
  a promise per listener, and tool declarations are serialized without a JSON round-trip: about 34–36% fewer instructions per
  streamed event in JSON, RPC and ACP mode (a 20,000-event answer: 41% less CPU), 18% in text mode, and 12–44% less per tool
  turn (7 to 67 tools). The output bytes are the same.
- **Streaming:** the blocks of a reply that are settled are not lexed and rendered again for each chunk: 10–12% less CPU while
  a long Markdown answer streams (identical frames over 16,500 fuzzed documents).

### Typing

- **`@file` completion** lists a folder once per completion and filters in memory: each key after the first takes under 1 ms
  instead of 16–22 ms (on a 1.46 million-file tree, 0.2 ms instead of up to 1.3 s), and a superseded listing is stopped.
- **Long prompt lines:** a key on a 2,000-character line costs 8x fewer instructions, on an 8,000-character line 13x.

### Tools and sessions

- **`ls`** of a 1,161-entry folder: about 3 ms instead of 30 ms.
- **`/resume`** lists 395 sessions (59 MB) in 250 ms instead of 770 ms, and in 100 ms from then on: it skips the lines it does
  not show, and keeps an index (`.session-index.json`) checked against each file's size and times.
- **Session appends** keep the file open (not on Windows): 18 µs instead of 70 µs each, with each entry written before the
  append returns, as before.
- **`read` of a large file** decodes only the part shown: a 128 MB log with an offset takes 170 ms and 67 MB of memory instead
  of 340 ms and 335 MB.

### Lighter

- **Memory in long sessions:** the TUI no longer keeps the full output of finished tool calls, and a file read again unchanged
  shares the earlier string: with 1.3 MB of bash output per prompt, the live heap after 30 prompts is 18 MB instead of 91 MB.
- **Smaller downloads:** the release archives no longer carry the documentation's images, and the x86-64 `.tar.xz` archives
  use xz's x86 filter: 4–6% smaller.

### Engine

- **JSON:** escaping a string that has one character outside Latin-1 (an em dash, an arrow) goes 16 characters at a time on
  ARM64: 16–34% fewer instructions for such strings.
- **`await`:** the engine's cache for resuming async functions lasts across microtask drains: 26% fewer instructions per
  `await` when many async functions take turns, 8% per streamed event in the event pipeline's micro-benchmark.

### Install

```bash
curl -fsSL https://pi-bolt.opensec.in/install.sh | sh
```

```powershell
irm https://pi-bolt.opensec.in/install.ps1 | iex
```

```bat
powershell -c "irm https://pi-bolt.opensec.in/install.ps1 | iex"
```

or `pi-bolt update`, or `npm install -g --allow-scripts=pi-bolt pi-bolt`, or `bun add -g --trust pi-bolt`.
